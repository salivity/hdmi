HDCP Authentication Handshake Over HDMI DDC

High-bandwidth Digital Content Protection (HDCP) relies on an initial cryptographic handshake executed over the HDMI Display Data Channel (DDC)—an I2C-based serial communication link. This article outlines the specific cryptographic exchange that takes place across the DDC line, detailing how the transmitter (source) and receiver (sink) exchange keys, verify credentials, derive shared secrets, and confirm synchronization before protected digital video is transmitted.

The Communication Medium: HDMI DDC

The HDMI connector dedicates physical pins 15 (DDC Clock / SCL) and 16 (DDC Data / SDA) to the DDC interface. While primarily used for reading Extended Display Identification Data (EDID), the DDC is also the transport mechanism for the HDCP control register interface (typically addressed at I2C slave address 0x74 for HDCP 1.x). The entire pre-encryption exchange occurs via byte-level reads and writes across this bus.

HDCP 1.x Handshake: The KSV Exchange and \(R_0\) Verification

The traditional HDCP 1.x handshake consists of a three-step protocol carried out over the DDC:

  1. Exchange of Nonces and Key Selection Vectors (KSVs):

    • The source initiates authentication by generating a pseudo-random 64-bit value (\(A_n\)) and writing it to the sink via DDC.
    • The source writes its 40-bit Key Selection Vector (\(A_{ksv}\)) to the sink.
    • The source reads the sink’s 40-bit Key Selection Vector (\(B_{ksv}\)) over the DDC.
    • Both devices verify that the received KSV contains exactly twenty 1s and twenty 0s to confirm standard format validity, and the source checks \(B_{ksv}\) against a revocation list.

  2. Derivation of the Shared Secret (\(K_m\)):

    • Both devices maintain an internal array of forty 56-bit secret device keys.
    • The source sums the secret keys indexed by the 1 bits in \(B_{ksv}\).
    • The sink sums the secret keys indexed by the 1 bits in \(A_{ksv}\).
    • If both sets of keys are mathematically valid, both calculations result in the exact same 56-bit shared secret value (\(K_m\)).

  3. Cipher Initialization and \(R_0\) Verification:

    • Both devices load \(K_m\), \(A_n\), and optional repeater data into their internal HDCP cipher blocks to generate a stream cipher state.
    • Both source and sink produce a 16-bit verification value, denoted as \(R_0\) (on the source) and \(R_0'\) (on the sink).
    • The source reads \(R_0'\) from the sink across the DDC within 100 milliseconds of transmitting \(A_n\).
    • If \(R_0 == R_0'\), authentication is successful, and uncompressed encrypted video transmission begins over the TMDS lines.
    • To maintain link integrity, the source periodically reads updated 16-bit values (\(R_i'\)) over the DDC roughly every 128 frames (or approximately every 2 seconds) and compares them to local \(R_i\) values.

HDCP 2.x Handshake: Authentication and Key Exchange (AKE)

For modern ultra-high-definition content using HDCP 2.2 or HDCP 2.3, the cryptographic protocol shifts from proprietary linear feedback shift registers to industry-standard asymmetric and symmetric cryptography, while still utilizing the DDC:

  1. Initiation and Public Key Exchange:

    • The source sends an AKE_Init message containing a 64-bit random nonce (\(r_{tx}\)) via DDC.
    • The sink responds with AKE_Send_Cert, providing a public-key certificate containing an RSA 1024-bit (or 3072-bit in newer revisions) public key signed by the Digital Content Protection (DCP) LLC, alongside a 64-bit receiver nonce (\(r_{rx}\)).

  2. Master Key Exchange:

    • The source verifies the sink's DCP certificate signature.
    • The source creates a 128-bit master key (\(k_m\)) and encrypts it using the sink’s RSA public key.
    • The source writes this encrypted payload (AKE_No_Stored_km) to the sink over DDC.
    • The sink decrypts the payload using its private key, resulting in both devices holding \(k_m\).

  3. Locality Check:

    • To prevent routing content across network extenders, the source writes LC_Init containing a 64-bit nonce (\(r_n\)) to the DDC.
    • The sink calculates a hash \(L'\) using HMAC-SHA256 based on \(r_n\) and the derived keys, then sends it back via DDC.
    • The source compares \(L\) and \(L'\) while enforcing a strict round-trip response deadline (typically under 20 milliseconds).

  4. Session Key Derivation:

    • Once the locality check succeeds, the source derives a 128-bit session key (\(k_s\)) using AES-128-CTR and sends an encrypted session key message (SKE_Send_Eks) over DDC.
    • This session key directly initializes the AES-128 engine that encrypts the main HDMI audio/video streams.
