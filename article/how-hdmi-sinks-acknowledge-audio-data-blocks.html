How HDMI Sinks Acknowledge Audio Data Blocks

In HDMI transmission, an HDMI sink does not actively acknowledge the receipt of uncompressed multi-channel audio data blocks on a packet-by-packet basis. Unlike bidirectional networking protocols that use ACK/NACK signaling to confirm packet delivery, HDMI relies on a unidirectional, feed-forward architecture. The sink accepts continuous streams of data over Transition Minimized Differential Signaling (TMDS) or Fixed Rate Link (FRL) lines, relying on pre-negotiated capabilities, forward error correction, and clock regeneration rather than real-time return receipts.

The Feed-Forward Architecture of HDMI Audio

Uncompressed multi-channel audio (such as Linear PCM) is transmitted from the source (transmitter) to the sink (receiver) during horizontal and vertical blanking intervals within structures known as Data Island periods. These data blocks are formatted into Audio Sample Packets (ASP).

Because the primary AV data path is strictly unidirectional, the sink has no physical back-channel within the main TMDS or FRL links to notify the source that an individual audio data block was successfully received. Transmission is continuous and real-time; the source assumes the sink is receiving and decoding the packets at the rate they are sent.

Forward Error Correction and Packet Verification

Instead of requesting retransmission upon packet loss or corruption, the sink detects and mitigates transmission errors locally:

  • BCH Error Correction: Every Data Island packet header and subpacket includes BCH error-correcting code parity bits. The sink uses this parity data to detect errors and correct single-bit errors in real time.
  • Error Concealment: If an audio data block is corrupted beyond what the BCH code can repair, the sink does not request a re-send. Instead, the sink discards the corrupted audio samples and conceals the drop-out (for instance, by interpolating adjacent audio samples, repeating the previous sample, or briefly muting the output) to prevent audible clicks or pops.

Pre-Transmission Capability Handshake (EDID)

The only communication regarding the sink's ability to receive audio occurs prior to transmission across the Display Data Channel (DDC), an \(I^2C\) bus:

  1. EDID Negotiation: When connected, the sink provides its Extended Display Identification Data (EDID) to the source.
  2. Short Audio Descriptors (SADs): The EDID contains CEA/CTA-861 Extension blocks that specify the sink’s audio support, including maximum channel count (e.g., 6-channel or 8-channel LPCM), supported sampling frequencies (such as 44.1 kHz, 48 kHz, or 192 kHz), and bit depths (16, 20, or 24 bits).
  3. Format Alignment: The source reads this profile and formats the uncompressed multi-channel audio data blocks to match parameters the sink is guaranteed to support.

Clock Synchronization via Audio Clock Regeneration (ACR)

To process audio packets correctly without flow-control acknowledgments, the sink must remain in precise timing alignment with the source:

  • The source transmits Audio Clock Regeneration (ACR) packets containing two values: Cycle Time Stamp (\(CTS\)) and a multiplier (\(N\)).
  • The sink uses these values alongside the incoming pixel clock to recreate the original audio master clock (\(128 \times f_s\)) via an internal phase-locked loop (PLL).
  • This continuous clock tracking ensures the sink’s audio buffer does not suffer from underflow or overflow, removing the need for receipt acknowledgments or transmission pacing.
