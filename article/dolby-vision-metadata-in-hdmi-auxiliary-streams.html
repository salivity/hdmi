Dolby Vision Metadata in HDMI Auxiliary Streams

This article explains how an HDMI source device packages and transmits Dolby Vision dynamic metadata across an HDMI interface using auxiliary stream structures. It details the underlying transport mechanisms within HDMI blanking intervals, the specific structures of Dolby Vendor-Specific InfoFrames (VSIF) and CTA-861 Extended Metadata Packets (EMP), and how the metadata payload is serialized and protected for accurate decoding by a sink display.

HDMI Data Island Architecture and Auxiliary Streams

HDMI transmits video data during active video periods, while non-video data—including audio, clock signals, and metadata—is transmitted during the horizontal and vertical blanking intervals. These blanking intervals are formatted as Data Island periods.

To deliver dynamic HDR metadata alongside the video stream without altering active pixel values, the HDMI source packages metadata into discrete 32-byte data packets within these Data Island periods. Each packet consists of a 4-byte header and a 28-byte payload, protected by Bose-Chaudhuri-Hocquenghem (BCH) error-correcting code (ECC) parity bits to ensure integrity during TMDS (Transition-Minimized Differential Signaling) or FRL (Fixed Rate Link) transmission.

Signatures and InfoFrame Identification (VSIF)

Dolby Vision relies heavily on the Vendor-Specific InfoFrame (VSIF) defined by the CTA-861 standard for signaling and low-bandwidth payload delivery. When an HDMI source identifies a Dolby Vision-capable sink via Extended Display Identification Data (EDID), it generates an InfoFrame containing:

  • Packet Type Identifier: Set to 0x81 to declare an auxiliary InfoFrame.
  • InfoFrame Type and Version: Identifies the specific payload generation and structure.
  • IEEE Organizationally Unique Identifier (OUI): Set to Dolby Laboratories’ registered 24-bit identifier (0x00D046).

The presence of this IEEE OUI informs the sink processor that the enclosed auxiliary data contains proprietary Dolby Vision configuration parameters rather than standard static HDR (CTA-861.3 Dynamic Range and Mastering InfoFrames).

Packaging the Dolby Vision Reference Processing Unit (RPU)

The dynamic metadata governing frame-by-frame or scene-by-scene tone mapping is generated as a Reference Processing Unit (RPU) payload. How this RPU is packaged into the auxiliary stream depends on the transmission architecture:

1. Extended Metadata Packets (EMP)

In modern implementations conforming to CTA-861-G/H and HDMI 2.1, large dynamic metadata sets (such as SMPTE ST 2094-10, the standardized variant of Dolby Vision) are transported using Extended Metadata Packets (EMP).

Because an RPU can exceed the 28-byte payload limit of a single auxiliary packet, the HDMI source fragments the RPU:

  • Fragmentation: The source splits the dynamic metadata bitstream into sequential segments.
  • Header Sequencing: Each EMP includes sequence markers (such as "First," "Continuation," or "Last" packet flags) and a sequence index to ensure deterministic reassembly.
  • Synchronization: The packets carry a synchronization timestamp or are tied directly to the frame counter of the upcoming video frame, ensuring that the target display applies tone mapping to the exact frame for which it was computed.

2. Low-Latency Dolby Vision (LLDV / Player-Led) Auxiliary Signaling

In Player-Led mode, tone mapping occurs within the playback source rather than the display. However, the source must still transmit colorimetry and configuration instructions via the auxiliary stream. In this case, the Dolby VSIF payload carries compact dynamic run-time properties—such as target luminance, color space flags (e.g., standard BT.2020 vs. IPT), and back-end display mapping parameters—directly inside a single or minimal set of VSIF auxiliary packets, bypassing the need for heavy RPU data chunking.

3. Standard Display-Led Tunneling (Legacy HDMI 1.4/2.0)

In standard "RGB Tunneling" mode, the full RPU metadata is actually packed into the least significant bits (LSBs) of the active 8-bit or 12-bit video stream to circumvent older HDMI bandwidth and InfoFrame size constraints. In this scenario, the auxiliary stream's primary function is signaling: the VSIF is injected into the Data Island to alert the display's HDMI receiver that the incoming standard 8-bit RGB 4:4:4 raster is not standard video, but rather an encrypted, metadata-multiplexed Dolby Vision composite container that must be un-tunnelled.

Serialization and Transmission

Once the source formats the metadata into the appropriate InfoFrames or EMPs:

  1. Checksum Generation: A validation checksum is calculated across the payload bytes and written to the packet header.
  2. Channel Allocation: The packet bytes are converted into HDMI Data Island characters using TMDS Error Reduction Coding (TERC4) or FRL packet mapping.
  3. Insertion: The packets are multiplexed onto the high-speed data lanes during the vertical blanking interval (VBI) preceding the target video frame.

This guarantees that the sink display parses, verifies, and applies the tone-mapping parameters before the first active video line of the associated frame is decoded.
