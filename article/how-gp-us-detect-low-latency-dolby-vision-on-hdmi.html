How GPUs Detect Low-Latency Dolby Vision on HDMI

When an HDMI sink is connected, a GPU driver determines whether it supports Low-Latency Dolby Vision (LLDV)—also known as Player-Led Dolby Vision—by querying and parsing the display’s Extended Display Identification Data (EDID). Specifically, the driver reads the CTA-861 extension blocks over the Display Data Channel (DDC) and inspects the Dolby Vendor-Specific Data Block (VSDB) for designated capability flags that indicate support for player-side tone mapping and 12-bit YUV 4:2:2 transport.

1. EDID Retrieval via the Display Data Channel (DDC)

Upon an HDMI Hot Plug Detect (HPD) interrupt, the GPU driver initiates an I2C communication over the DDC lines to read the sink device’s EDID. A standard 128-byte base EDID does not contain HDR-specific capabilities. Therefore, the driver searches for additional 128-byte CTA-861 (formerly CEA-861) extension blocks, which house advanced video, audio, and vendor-specific configuration data.

2. Locating the Dolby Vendor-Specific Data Block (VSDB)

Within the CTA-861 extension block, the driver traverses the Data Block Collection looking for a Vendor-Specific Data Block (Tag 3). A Dolby block is positively identified by reading the 24-bit IEEE Organizationally Unique Identifier (OUI):

  • Dolby IEEE OUI: 0x00, 0xD0, 0x46 (stored in little-endian format as 46-D0-00).

Once the driver matches this OUI, it knows the remaining bytes define Dolby Vision profiles, timing, and processing parameters supported by the sink.

3. Parsing the Dolby VSDB Version

Dolby VSDBs generally come in different payload structures, designated by version formats:

  • Version 1 (V1): Primarily used for early Display-Led implementations (RGB 8-bit tunneling).
  • Version 2 (V2): Introduces configurable flags to support both standard Display-Led and Low-Latency (Player-Led) modes.

The driver checks the length and internal version byte of the payload. If the block matches the Version 2 structure (typically 12 to 15 bytes in total length), the driver proceeds to decode low-latency capabilities.

4. Reading Low-Latency Flags and Color Formats

Inside the Version 2 Dolby VSDB, specific bitfields declare low-latency support:

  • Interface / Low-Latency Bit: The driver inspects the profile capability byte (often Byte 5 in standard V2 implementations). A designated bit within this byte explicitly signals support for Low-Latency Mode. If set to 1, the sink device can accept pre-tone-mapped Dolby Vision content.
  • Supported Color Spaces: The driver reads accompanying bits that specify compatible pixel formats for the low-latency stream. Unlike standard Dolby Vision, which packages 12-bit data into an RGB 4:4:4 8-bit container via proprietary tunneling, LLDV transmits uncompressed 10-bit or 12-bit YUV 4:2:2 or YUV 4:4:4 signals.
  • Target Luminance and Colorimetry: The driver reads minimum/maximum luminance values and primary color coordinates embedded in the block. These parameters are essential for the GPU's internal composition engine to perform tone mapping accurately before sending the signal.

5. Driver Configuration and Handshake

If the bitfield flags confirm LLDV support:

  1. The driver registers the display as an LLDV-capable sink with the operating system's color and display management stack.
  2. When Dolby Vision content playback begins, the GPU performs the tone-mapping calculations locally using the sink's advertised luminance parameters.
  3. The GPU switches the HDMI output to the negotiated pixel format (typically 12-bit YUV 4:2:2) and begins embedding Dolby Vision Dynamic Range and Mastering InfoFrames (or vendor-specific InfoFrames) into the HDMI blanking interval, signaling the TV to bypass its internal tone mapper and apply only picture calibration.
