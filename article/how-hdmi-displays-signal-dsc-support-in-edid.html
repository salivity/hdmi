How HDMI Displays Signal DSC Support in EDID

An HDMI display signals its Display Stream Compression (DSC) decompression capability to a source device by declaring a dedicated HDMI Forum DSC Data Block within a CTA-861 extension in its Extended Display Identification Data (EDID). Defined under the HDMI 2.1 specification, this data block informs the GPU or source video processor that the sink can decompress DSC 1.2 streams, outlining critical hardware limits such as supported color depths, slice configurations, pixel formats, buffer sizes, and the maximum supported Fixed Rate Link (FRL) rates.

The CTA-861 Extension Mechanism

Standard base EDID (Block 0) provides 128 bytes of basic legacy display information, which is insufficient for HDMI 2.1 capabilities. To communicate advanced features like DSC, displays append one or more CTA-861 extension blocks (typically Block 1 or beyond).

Within the CTA-861 extension, data is structured into sequential Tag-Length-Value (TLV) data blocks. While HDMI 2.0 introduced the HDMI Forum Vendor-Specific Data Block (HF-VSDB) for link configuration, HDMI 2.1 introduced the HDMI Forum DSC Data Block (HF-DSC Data Block) as an Extended Tag Data Block specifically designed to detail compression support.

Key Fields in the HDMI Forum DSC Data Block

When an HDMI source reads the sink’s EDID over the Display Data Channel (DDC/I2C), it parses the HF-DSC Data Block to extract specific hardware capabilities:

  • DSC Version Support (DSC_1p2): A dedicated bit flag indicates whether the display supports DSC 1.2 decompression.
  • Bit Depth Capabilities: Specific flags declare support for decompressed color depths beyond baseline 8-bit, including:
    • DSC_10bpc: 10 bits per component support.
    • DSC_12bpc: 12 bits per component support.
    • DSC_16bpc: 16 bits per component support.
  • Native Pixel Formats: Displays advertise support for native chroma formats, such as DSC_Native_420, indicating whether the decoder can directly decompress native YCbCr 4:2:0 streams without prior upsampling.
  • Target Bit-per-Pixel (DSC_ALL_BPP): A bit flag that signifies whether the sink supports all fractional/integer bits-per-pixel rates or is limited to specific targets.
  • Maximum Slice Count (DSC_Max_Slices): DSC relies on dividing video frames horizontally into independent slices. The display advertises its slice decoding capability through defined values (e.g., up to 1, 2, 4, 8, 12, or 16 slices). This dictates how many parallel compression engines the GPU source must allocate.
  • Maximum DSC Link Rate (DSC_Max_FRL_Rate): Indicates the highest FRL lane configuration and speed (from FRL 3 Gbps up to 12 Gbps per lane, across 3 or 4 lanes) that can be utilized concurrently with DSC.
  • Buffer Memory Allocation (DSC_TotalChunkKBytes): Specifies the display's internal buffer memory allocated for handling DSC multiplexing and decompression, ensuring the source does not overflow the sink's slice buffers.

Operational Workflow

During the initial HDMI connection handshake:

  1. EDID Readout: The source requests the base EDID and CTA-861 extensions via the I2C-based DDC interface.
  2. Parsing: The graphics driver identifies the HF-VSDB (to evaluate FRL capabilities) and the HF-DSC Data Block.
  3. Link Decision: If a user selects a resolution, refresh rate, and color format (e.g., 4K at 144Hz 10-bit RGB) that exceeds the display’s uncompressed FRL bandwidth, the GPU checks the HF-DSC parameters.
  4. Encoding: If the format falls within the display's advertised slice count, bit depth, and buffer constraints, the GPU engages its hardware DSC encoder and configures the transmission over the HDMI FRL lanes accordingly.
